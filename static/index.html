Walk the graph

People, commits and files become nodes. Files that change together get a weighted edge.

MATCH (f:File)-[e:CO_CHANGED_WITH]->(o:File)
WHERE f.path IN $files
  AND NOT o.path IN $files
RETURN o.path, e.weight

Good questions.

Does it use an LLM?

The merge gate does not: it is graph queries, so it is fast and gives the same answer twice. The Ask page uses a model only to choose between six fixed graph tools and to phrase the result, and an answer that names a file not found in the evidence is withheld.

How accurate is it?

On GraphRAG-SDK the gate puts a deliberately hidden file in its top three companions 35% of the time, against 14% for guessing the most-changed files. On the much smaller falkordb-py it is 20% against 18%. It is a useful signal on a large active repository, not proof of anything. The Proof page shows the live numbers.

Is it safe to point at my repository?

It reads public repositories through git log and never executes their code. This demo has no authentication, so do not use it for private code.

What does it need to run?

FalkorDB (one Docker command) and git. A model API key is needed only for the Ask page. The merge gate and the recorded run work without one.

What can't it do?

It is not a static analyser, so it cannot see imports that have never changed together. It does not read PR comments or issues yet. New files have no history, so they are reported as unknown rather than safe.

Why FalkorDB?

The gate walks relationships on every request: PageRank, multi-hop co-change and shortest path in milliseconds. And one instance holds a separate graph per user for the agents' memory, with no extra deployments.

How the score is made

  • Load-bearing (35): PageRank over the co-change graph. Docs and lockfiles are ignored.
  • Missing companions (40): files that changed with these in 25%+ of their commits but aren't in this change.
  • Spans modules (10) and size (15).
  • The verdict compares the score with the repository's own past changes (HIGH above the 80th percentile, MEDIUM above the 50th).
  • Every point is shown next to its reason. There is no hidden model score.

What the AI can and can't do

  • The gate itself uses no LLM: graph queries only, so it is fast and repeatable.
  • The Ask page's model picks from six fixed, parameterised tools. It never writes Cypher.
  • Answers may only name files found in the evidence, or they are withheld.
  • History is read with git log; no repository code is ever run.

Known gaps (we'd rather say so)

  • Co-change is a statistical signal, not a dependency analysis.
  • It is weak on small or young repos: see the lift above.
  • Demo PRs are already merged, so their own commits are part of the history.
  • Decisions come from commit messages only; PR comments and issues are not ingested yet.

Use it where you work.

Three ways to put the gate in front of every change. All of them call the same graph; none needs an LLM key except the agents.

In CI: comment on every PR, fail on HIGH

A small script with no dependencies and a workflow that runs it. It never breaks your build because the server was down, unless you pass --strict.

name: blindspot-gate
on: { pull_request: { types: [opened, synchronize, reopened] } }
jobs:
  gate:
    runs-on: ubuntu-latest
    permissions: { pull-requests: write, contents: read }
    steps:
      - uses: actions/checkout@v4
      - id: gate
        run: |
          set +e
          python integrations/gate_ci.py --url "${{ vars.BLINDSPOT_URL }}" \
            --pr "${{ github.event.pull_request.html_url }}" --fail-on HIGH --markdown comment.md
          echo "code=$?" >> "$GITHUB_OUTPUT"
      - if: hashFiles('comment.md') != ''
        run: gh pr comment "${{ github.event.pull_request.number }}" --body-file comment.md
        env: { GH_TOKEN: "${{ github.token }}" }
      - if: steps.gate.outputs.code == '1'
        run: exit 1

Limits: the repository must already be added to your Blindspot instance and must be public, because the server reads the pull request from GitHub.

From any script: one request

curl -s -X POST "$BLINDSPOT_URL/api/gate" \
  -H 'Content-Type: application/json' \
  -d '{"pr_url": "https://github.com/FalkorDB/GraphRAG-SDK/pull/335"}'
# or, without GitHub: -d '{"repo": "repo", "files": ["graphrag_sdk/src/graphrag_sdk/storage/graph_store.py"]}'

The response includes verdict, score, percentile, factors (each with its points), companions, reviewers, decisions and a check_id you can open at #check/<id>.

What Blindspot can and can't do.

A review tool earns trust by being clear about its limits. This page is the short version.

Capabilities

QuestionAnswer
Reads git history of public repositoriesYes, with git log and git ls-tree
Runs code from the repositoryNever
Writes to GitHub or changes your repositoryNever. It is read-only; the gate only shows a verdict.
Uses an LLM for the merge-gate scoreNo. Graph queries only.
Uses an LLM on the Ask pageYes, to pick one of six fixed tools and phrase the answer
Lets the model write queriesNever. Tools are parameterised and file names are resolved against the graph.
Calls an unknown file "safe"Never. It reports it as unknown.
Keeps a record of every verdictYes: a hash-chained audit log in the graph. It detects edits; it is not a signature.

What is stored

The repository graph (people, commits, files, co-change edges), one memory graph per Ask user (their questions, answers and a few facts), and a coordination graph recording each agent step. All live in FalkorDB.

Known gaps

  • Co-change is statistical. It cannot see a dependency that has never changed together. On small or young repositories it is weak: the Proof page shows ×1.2 on a 330-commit repository.
  • Verdict thresholds are heuristic. HIGH means riskier than 80% of this repository's own past changes and MEDIUM riskier than 50%. They are not calibrated against real incidents or defects.
  • Demo pull requests are already merged, so their own commits are part of the history the gate reads.
  • "Decisions" come from commit messages only. Pull request comments and issues are not ingested yet.
  • No authentication. Per-IP rate limits protect the costly endpoints (Ask 8/min, add a repository 4/min, gate 60/min) and responses carry basic security headers, but anyone who can reach the site can use it. Do not expose it with an uncapped paid model key.
  • GitHub's anonymous API limit (60 requests an hour) applies to pull-request lookups; results are cached for an hour.
